# 운영 app.needs 에 있으나 이 체크아웃의 contracts/ddl/needs/*.sql 로는 만들어지지 않는 객체.
# 포크가 운영에 DDL 을 올리면 이 파일에 한 줄을 PR 로 보낸다 -- 남의 DDL 이 운영에 들어오면 선언한다.
#
# 원장(needs.schema_migration)이 아니라 이 파일이 기준인 이유: 원장에 020 이 있어도 그 파일은 이
# 체크아웃에 없어 기대치를 조립할 수 없다. 남이 올린 DDL 은 조립되는 것이 아니라 선언되는 것이다.
#
# tool/checks/ddl-drift 만 읽는다. 한 줄에 객체 하나, '#' 뒤는 주석:
#   <table>           테이블 전체. 운영 pg_dump 에서 -T needs.<table> 로 빠진다.
#   <table>.<column>  컬럼 하나. pg_dump 에 컬럼 제외가 없어서, 운영 덤프를 일회용 postgres 에
#                     되돌린 뒤 DROP COLUMN 하고 다시 덤프한다.
#
# 여기 없는 남의 객체가 운영에 있으면 ddl-drift 는 DRIFTED 로 실패한다 -- 그것이 이 파일의 값이다.
# 반대로 이 레포가 선언하는 테이블은 제외되면 안 된다: 제외하는 순간 그 테이블의 드리프트가
# 영원히 안 보인다.
#
# 그런데 "이 레포" 가 하나가 아니다. 이 파일이 존재하는 이유가 바로 또 다른 레포가 있다는 사실이고,
# 그 레포로 머지되면 같은 아홉 줄이 뜻을 뒤집는다 -- upstream cosmai 체크아웃에는 020~025 가 없어
# 아홉이 전부 남의 것이지만, 포크 cosmai-import-ydc 체크아웃에는 020~025 와 그 뷰들이 있어 아홉이
# 전부 자기 선언이다 (cosmai#108). 그래서 판정을 이 목록이 아니라 **체크아웃**에 묻는다:
# 이 체크아웃이 선언하는 객체는 무시한다 -- 목록에 있어도 제외하지 않고 기대치와 그대로 맞댄다.
# 규칙은 tool/ddl-foreign-entries 한 자리에 있고, 무시가 검사를 약하게 만들지 않는 이유도 거기 있다:
# 무시된 객체는 기대치에도 서고 운영 덤프에도 남아 여전히 대조된다. 둘 다 선언하면 둘 다 본다.
# upstream 에서는 아홉 중 어느 것도 선언되지 않아 이 규칙이 한 줄도 건드리지 않는다.
